# Creator library and filesystem boundary

`services/posts/library.ts` stores creator connections in the existing IndexedDB settings store. Keys include website origin, provider and creator ID. Jobs reference a connection but do not own it: removing a job leaves the registered handle, while explicitly clearing all extension data removes both. A new destination replaces its connection with auto sync off; it does not inherit the earlier folder's observation baseline.

Automatic sync and per-creator selection default off. The UI exposes an atomic Off / Check only / Auto sync mode change; switching to Off or Check only pauses scheduled automatic saves. A content-script site-visit event and the existing 30-second recovery alarm wake the serial scheduler. Each wake processes at most one due creator. Probes are limited to once every 30 minutes per creator, do not interrupt active work, and compare canonical post metadata rather than IDs alone. The initial comparison, an observed change or a seven-day deadline creates a durable scan/download job in Auto sync mode. Failed API checks do not advance successful-check timestamps. Permission errors retain the connection. Check only reads the recent page and never runs a full scan or downloads files.

Bulk actions use a separate persisted `creator-library-batch` setting. Check selected probes recent posts without folder access. Sync selected forces a full comparison even when recent metadata matches, or resumes that creator's pending library job. Selection is captured when the batch starts. Explicit batches work with automatic mode off and can finish in the background. The worker processes one creator at a time, waits behind active manual/ZIP work, respects shared host cooldowns, and skips blocked creators. Stop clears queued items and pauses only the batch's active save. Switching automatic mode does not stop an explicit batch. Clearing all extension data removes both settings and pending work.

Allow first-sync folders opens a top-level permission page using stored child handles from root discovery. Only selected creators without a completed full-sync baseline enter the queue; granted permissions, completed syncs and unselected creators are skipped. Folder names must match the saved creator, and readable JSON is checked before prompting. If read permission has expired, JSON is checked immediately after the explicit grant and again by the writing context. No root write permission, directory picker or file picker is used. Each request starts synchronously from its own Allow folder click, as required by [Chrome's File System Access permission model](https://developer.chrome.com/docs/capabilities/web-apis/file-system-access). The next folder loads automatically; cancellation/denial permits retry or Skip. The new authorization command validates access without starting or resuming a job. Scheduled automatic sync remains governed by its existing setting.

Persisted probe results distinguish a missing baseline, changed recent metadata, unchanged recent metadata, a weekly deadline, unreadable quick-page entries and retryable earlier file failures. Normal findings are not errors. The old ambiguous check-only warning is migrated conservatively: it never becomes evidence of confirmed updates. Cards show concise results; Details contains folder paths, explanations, errors and separate recent-check, complete-scan and sync-completion times. A fresh Check result can be shown while an older save is paused. Browser write permission is queried without prompting when the library is open, cached for 30 seconds, and refreshed on focus/visibility changes. A granted permission hides the access action; a missing handle offers reconnection. Archive JSON and containment are still validated at the writer, independently of that display.

Recent-list fingerprints are committed from the original probe response so hydrated details cannot cause perpetual false changes. Partially invalid quick pages schedule the existing tolerant discovery path. Rate-limit deadlines are persisted per origin and shared across creator probes and queued media tasks. A paused creator backs off without starving other eligible creators. Candidate fingerprint caches are scoped by destination/quality, file identity, size and modification time; a cache hit still requires a complete byte comparison before treating content as identical.

The portable sync history retains its v1 format with optional validated scope, text fingerprint and extraction digest fields. Legacy sync histories use their original manifest to recover single-post/subset scope where available. Source origins are never merged automatically. Text snapshots advance only for successfully saved selected text tasks; failed text and unselected posts cannot masquerade as saved revisions.

Read-only root discovery inspects immediate names, then candidate metadata. It does not recursively walk unrelated folders and never stores the root as a writing destination. The low-level relative writer validates creator name, JSON identity, allowed paths and resolved child containment inside its serialized write reservation. A missing/malformed primary history fails closed rather than falling back to stale metadata. New-folder initialization is a separate path requiring a freshly created empty directory. The old unrestricted parent-folder writer rejects all writes, including resumed legacy Discord folder jobs.

Filesystem writes close before success is recorded. Each file's completed state is persisted before batching a portable index update; its staged recovery bytes are not released before that update succeeds. Transient transfer progress stays in a bounded in-memory map rather than rewriting the whole job. Revision-keyed detail caches avoid recomputing unchanged metadata for every UI poll.

Large file transfers checkpoint immutable 8 MiB chunks inside the extension's private job cache when a strong ETag, known size and byte-range support are available. Resume sends `Range` and `If-Range`; partial responses must match the original validator, exact requested interval and total size. Invalid ranges/416 restart with a complete request, while a 200 response replaces the partial transfer. Weak validators and encoded/unknown-size responses cannot resume. Only fully closed chunks survive interruption; completion assembles a new staged file before removing private chunks. This uses extra temporary space and never uses the creator folder as a partial-download cache.

Exact source-hash deduplication and full byte comparisons remain enabled according to creator preferences. File collisions use bounded chunk comparisons. Extraction records a versioned SHA-256 identity over all 1 MiB chunks, bound to total file size, for both input and outputs. Source removal verifies those identities and archive ownership immediately before its single-file removal. Existing extraction conflicts are saved under a different filename; unverified legacy sources and all automatic-sync originals are retained.

The browser API supplies logical directory handles, not Windows reparse-point metadata. The implementation does not claim an OS-level no-follow guarantee for junctions or concurrently replaced filesystem objects. A native helper is needed if that stronger boundary is required. Tests verify logical handle escapes, name/JSON mismatches, invalid paths, same-size content changes and zero unrelated-folder mutations using disposable fixtures.

Validation: `npm run check` and the nine browser suites in `npm run release:check`, including `test:sync` and `test:permissions`. On environments where bundled-config temporary writes are restricted, use `npm test -- --configLoader native` and set `VITE_CONFIG_LOADER=native` for the build (Node with native TypeScript support required).
